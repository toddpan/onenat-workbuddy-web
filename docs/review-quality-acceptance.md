## 0. 结论摘要（放行结论建议）

**放行结论：需要改进（NEEDS WORK）。不建议按"生产就绪"放行；亦不构成"阻断"**（无产品路径数据丢失或安全孔洞的实测证据，现场实例在服务）。

## 4. 放行标准与压倒性证据清单

### 4.1 「登录阻塞成立」判定线（全部满足；测量法：任务窗口内序列 1rps×n≥30 + 一次 10 并发突发，连续 3 轮 ≥2 轮成立）
1. 登录 P95 ≥ max(5×空闲基线 P95, 1000ms)，或 ≥10% 样本 >2000ms，或出现 >5s 超时/连接拒绝；
2. healthz 探针（40-50ms 间隔）单次 ≥1000ms，或 30s 窗口内 ≥5 次 ≥500ms；
3. 堆栈/系统证据：sample 或 CPU profile 主线程非空闲采样占比 ≥50% 且热点落在 序列化/同步写盘/scrypt 帧，或 fs_usage 显示 store.json 落盘频率 ≈ delta 频率；
4. 排除自扰：无 A1 限速 429、无 B5 并发风暴混入。
（本机基线参考值：空闲登录 P50 21ms / P95 27ms；healthz P50 2-3ms；单次全量落盘 13.5ms@3.16MB。）

### 4.2 「修复有效」判定线（同规模/速率/并发下，全部满足）
1. 登录 P95 ≤ max(2×空闲基线, 150ms)，max ≤ 500ms，零超时；
2. healthz max ≤ 100ms，无 ≥500ms 停顿；
3. 落盘彻底移出 delta 路径：流式期间 store.json 写次数 ≤ 流时长/250ms ×1.2（fs_usage 计数）；
4. 功能门槛：`repro-long-turn.mjs` 7/7 + `test:unit` 全绿 + `smoke` 全绿 + 长回复尾部标记完整。

### 4.3 由「需要改进」升级为「生产就绪」所需的压倒性证据清单
1. C4 归因闭环：harness 修复后 7/7 全绿（若归因为产品缺陷则修复后复测）；
2. B1/B2/B3 编排路径实测：在 3.5MB 与 10MB store 下均满足 §4.1 未触发、且修复后满足 §4.2；

5. C5 浏览器矩阵通过记录（≥3 浏览器 × 登录/控制台/流式/监控）；
